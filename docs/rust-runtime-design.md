# Rust Runtime MVP Design

This document records the current Rust Runtime MVP behavior. It describes only the verified implementation under [`rust/`](../rust/) and does not redefine or replace the existing Python implementation.

## Scope

The Rust MVP covers five crates in the Cargo workspace (protocol, bus, runtime, cli, sdk). MVP core is protocol/bus/runtime/cli; sdk is FFI/SDK skeleton.

* [`rust/protocol`](../rust/protocol/) defines the event envelope, subject constants, and runtime payload structures.
* [`rust/bus`](../rust/bus/) provides an in-memory publish/subscribe bus for local runtime execution and tests.
* [`rust/runtime`](../rust/runtime/) provides runtime lifecycle state, task tracking, worker lookup, LLM mediation via injected provider, tool mediation via ToolRegistry, user handler registration, and bus-backed publish/handle behavior.
* [`rust/cli`](../rust/cli/) provides the local command surface, including the deterministic demo path.

The MVP keeps the Python runtime path compatible with the broader project. Rust is documented as an implemented workspace subset, not as a replacement for Python.

## Protocol Contract

[`EventEnvelope`](../rust/protocol/src/message.rs:5) is the Rust runtime event envelope. It includes canonical fields for `id`, `type`, `subject`, `source`, `timestamp`, `schema`, `payload`, `correlation_id`, `causation_id`, and `metadata`, plus optional current extension fields `scope` and `refs`.

Runtime payloads live in [`rust/protocol/src/payload.rs`](../rust/protocol/src/payload.rs). The MVP includes [`RuntimeAgentSpawnPayload`](../rust/protocol/src/payload.rs:5), [`RuntimeTaskAssignPayload`](../rust/protocol/src/payload.rs:10), [`RuntimeTaskResultPayload`](../rust/protocol/src/payload.rs:24), [`RuntimeAgentReadyPayload`](../rust/protocol/src/payload.rs:34), [`RuntimeAgentExitPayload`](../rust/protocol/src/payload.rs:41), [`RuntimeToolRequestPayload`](../rust/protocol/src/payload.rs:47), [`RuntimeToolResultPayload`](../rust/protocol/src/payload.rs:56), [`RuntimeLLMRequestPayload`](../rust/protocol/src/payload.rs:70), [`RuntimeLLMResponsePayload`](../rust/protocol/src/payload.rs:82), and [`RuntimeAgentErrorPayload`](../rust/protocol/src/payload.rs:98). Payload-level `correlation_id` is carried by task, LLM, and tool request/result payloads so the runtime can preserve request correlation independently of generated event envelope ids and timestamps.

Subject constants live in [`rust/protocol/src/subject.rs`](../rust/protocol/src/subject.rs). The MVP includes agent spawn/ready/exit/error subjects, task assign/result subjects, LLM request/response subjects, and tool request/result subjects. Dynamic task assignment subjects are generated by [`runtime_task_assign_for_agent()`](../rust/protocol/src/subject.rs:8).

## Validation and Normalization

[`validate_and_normalize_payload()`](../rust/protocol/src/validation.rs:48) validates and normalizes payloads for canonical subjects. For canonical subjects, it deserializes to the corresponding struct to validate, then re-serializes to normalize. For unknown/extension subjects, it returns the payload unchanged. Invalid canonical payloads return `ValidationError` and are NOT recorded by the bus.

For `runtime.llm.request` and `runtime.tool.request` subjects, `request_id` is auto-completed from the event id if not present. This ensures every recorded request payload has a `request_id`.

## Publish Flow

`Runtime::publish()` is the **sole event entrance**. It performs only:

1. Generate `event_id`
2. Call `validate_and_normalize_payload()`
3. Create `EventEnvelope`
4. Call `bus.publish()`
5. Return envelope

It does NOT directly process the event, update state, or invoke providers/tools.

## Bus Contract

[`BasicBus`](../rust/bus/src/lib.rs:84) is the in-memory MVP bus. It implements `Clone + Send + Sync + 'static`. All methods take `&self` and use internal mutability via `RwLock`.

The [`MessageBus`](../rust/bus/src/lib.rs:58) contract supports subscribe, publish, unsubscribe, close, closed-state inspection, and handler-count inspection — all via `&self`.

Current publish semantics are:

* [`publish()`](../rust/bus/src/lib.rs:147) returns a closed-bus error if the bus has been closed.
* Publishing to a subject with no subscribers succeeds.
* Every accepted envelope is appended to [`published_events()`](../rust/bus/src/lib.rs:102) before handler execution.
* Handlers are cloned first, then the lock is released before awaiting handlers. This prevents deadlock when a handler publishes to the same bus.
* [`SubscriptionId`](../rust/bus/src/lib.rs:48) implements `Debug + Clone + PartialEq + Eq + Hash`.

These semantics support deterministic local testing without requiring NATS for the MVP path.

## Runtime Core Architecture

### RuntimeCore

[`RuntimeCore`](../rust/runtime/src/runtime.rs:35) holds shared state:

* `bus` — the message bus
* `worker_registry` — agent lifecycle tracking
* `task_states` — task state storage
* `llm_provider` — the LLM provider (via `Arc<RwLock<Arc<dyn LlmProvider>>>`)
* `tool_registry` — tool registration and lookup

### Internal Handlers

`start()` registers internal handlers for all canonical subjects. These handlers are registered **once** and cannot be duplicated. Internal handlers:

1. Process the event (update state, call provider/tool)
2. Publish only the result envelope to the bus (do NOT re-publish or forward the original envelope)

Internal subjects:

* `runtime.agent.spawn` — observation only in MVP
* `runtime.agent.ready` — calls `WorkerRegistry.mark_ready`
* `runtime.agent.exit` — calls `WorkerRegistry.mark_exited`
* `runtime.agent.error` — calls `WorkerRegistry.mark_error` only if `agent_id` is present
* `runtime.task.assign` — creates/updates `TaskState`, sets status to `Assigned`
* `runtime.task.result` — saves result/error, updates status
* `runtime.llm.request` — marks task `WaitingForLlm`, calls provider once, publishes `runtime.llm.response`
* `runtime.tool.request` — marks task `WaitingForTool`, calls tool once, publishes `runtime.tool.result`

### User Handlers

Users can register handlers via `register_handler(subject, handler) -> Result<SubscriptionId, RuntimeError>`. User handlers:

* Are registered independently from internal handlers
* Can be registered for the same subject as internal handlers
* Cannot override internal handlers
* Multiple user handlers can be registered for the same subject

User handlers are unsubscribed via `unregister_handler(id) -> Result<(), RuntimeError>`.

### LlmProvider Injection

Runtime holds `Arc<RwLock<Arc<dyn LlmProvider>>>`. Providers can be injected via `ThalamusRuntime::new()` or replaced via `set_llm_provider(provider)`.

Re-exported types:

* `thalamus_runtime::LlmProvider` — the trait
* `thalamus_runtime::MockLlmProvider` — deterministic mock (default)
* `thalamus_runtime::ErrorLlmProvider` — always returns `Err(RuntimeError::ProviderError(...))`

Provider errors result in `runtime.llm.response` with `status="error"`. The request `publish()` itself succeeds. Provider errors do NOT auto-fail tasks.

### ToolRegistry

[`ToolRegistry`](../rust/runtime/src/tool.rs:44) manages tool registration:

* `register(capability, tool)` — register a tool
* `register_alias(alias, target)` — register an alias for a tool
* `unregister(capability)` — remove a tool
* `get(capability)` — lookup a tool
* `list_capabilities()` — return sorted list of capabilities

The `Tool` trait:

* `capability()` — tool capability name
* `description()` — tool description
* `invoke(RuntimeToolRequestPayload)` — execute the tool

Default tools:

* `tool.echo` — canonical name
* `echo` — alias for backwards compatibility

Unknown tools result in `runtime.tool.result` with `status="error"` and `error.capability` set to the requested capability name. The request `publish()` itself succeeds.

### Generated Event Helpers

`llm.response` and `tool.result` envelopes are generated via private helpers in `RuntimeCore`:

* New `event_id` is generated
* `correlation_id` resolution order: `request_event.correlation_id` → `payload.correlation_id` → `request_event.id`
* `causation_id = request event id`
* Payload `request_id = request payload request_id`
* Payload `correlation_id = request payload correlation_id`

### Exact-Once Semantics

Each request subject (`runtime.llm.request`, `runtime.tool.request`) is processed by exactly one internal handler invocation. The handler:

1. Parses the request
2. Updates task state
3. Calls provider/tool exactly once
4. Publishes exactly one response/result envelope

### Lifecycle

> **重要: Start/Stop は daemon lifecycle ではない**
>
> `start()` および `stop()` は、プロセスの起動・終了を管理する daemon lifecycle 操作ではありません。これらは runtime の内部状態遷移とハンドラー管理のみを実行し、プロセスの生存期間を制御するものではありません。

#### start()

`start()` は以下の操作のみを実行します：

1. 内部ハンドラーを登録（各 canonical subject に対して一度だけ登録、重複不可）
2. 状態を `Running` に遷移

`start()` は既に実行中の場合に `LifecycleError` を返します。プロセスの起動、デーモン化、リスタートは行いません。

#### Runtime stop() の非冪等性

`stop()` は以下の操作のみを実行します：

1. 内部ハンドラーを unsubscribe
2. bus を close
3. 状態を `Running` → `Stopped` に遷移

`stop()` はプロセスの終了、シグナルハンドラー、リソース解放（ファイルディスクリプター等）を行いません。publish は closed bus エラーを返します。

**非冪等性保証**: `stop()` は非冪等です。初回の呼び出しのみ上記操作を実行し、状態を `Stopped` に遷移します。2回目以降の呼び出しは、既に `Stopped` 状態であるため `LifecycleError` を返します。複数回の呼び出しは許容されません。

#### CLI Command::Stop の冪等性

`CLICommand::Stop` は冪等性確保のため `stop()` を呼び出しません。状態を表示し、プロセス終了（exit/abort）も行いません。

**冪等性保証**: `stop()` を呼び出さないため、Runtime の状態を変更しません。複数回実行しても同じ結果（現在の状態表示）を返します。Runtime の状態遷移やリソース操作は一切行わないため、外部からの並列実行や誤った複数呼び出しにも影響を受けません。

#### Runtime stop() と CLI Stop の比較

| 項目 | Runtime::stop() | CLICommand::Stop |
|------|-----------------|------------------|
| 目的 | runtime内部pipelineを停止 | 停止要求をackする |
| 実行条件 | `Running`状態のみ成功 | 常に成功 |
| ハンドラーunsubscribe | 成功時に実行 | 実行しない |
| bus close | 成功時に実行 | 実行しない |
| 状態遷移 | `Running -> Stopping -> Stopped` | 実行しない |
| 2回目以降 | `LifecycleError` | `Ok(())` |
| 冪等性 | 非冪等 | 冪等ack |
| daemon停止 | 行わない | 行わない |

## CLI Contract

[`ThalamusCLI`](../rust/cli/src/lib.rs:19) defines the command-line surface. [`CLICommand`](../rust/cli/src/lib.rs:33) includes start, stop, status, list-agents, and [`RunDemo`](../rust/cli/src/lib.rs:203).

[`ThalamusCLI::run()`](../rust/cli/src/lib.rs:156) completes the local command paths. [`RunDemo`](../rust/cli/src/lib.rs:203) creates `BasicBus`, clones an observer, creates `ThalamusRuntime`, starts the runtime, publishes task.assign, llm.request, tool.request, and task.result events. Events are observed via `observer.published_events()`. Tool capability uses canonical `"tool.echo"`.

## Non-goals

The Rust MVP does not claim the following:

* Replacement of the existing Python implementation.
* Production NATS backend behavior for the Rust bus path.
* External MCP gateway mediation.
* Qdrant/indexer behavior.
* SDK/FFI expansion (sdk crate is FFI skeleton, not MVP core).
* ZooCodeCustom integration.
* Python runtime changes.
* Runtime restart support (restart is not implemented).

#### MessageBus Implementations

- **BasicBus**: local deterministic in-memory bus (default)
- **NatsBus**: optional distributed transport backend behind `nats` feature

#### NATS Backend (Optional)

`thalamus-bus` crate は optional feature `nats` として NATS 連携バックエンドを提供する。

- **Feature**: `nats`
- **実装**: [`NatsBus`](rust/bus/src/nats.rs)
- **依存**: `async-nats` (optional)

```toml
[features]
nats = ["dep:async-nats", "dep:futures"]

[dependencies]
async-nats = { version = "0.37", optional = true }
futures = { version = "0.3", optional = true }
```

使用例:

```toml
[dependencies]
thalamus-bus = { version = "0.1", features = ["nats"] }
```

[`NatsBus`](rust/bus/src/nats.rs) は [`MessageBus`](rust/bus/src/lib.rs:62) トレイトを実装し、MVP at-most-once transportとして動作する。

詳細は [NATS Backend Design](nats-backend-design.md) を参照。
