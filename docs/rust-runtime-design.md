# Rust Runtime MVP Design

This document records the current Rust Runtime MVP behavior. It describes only the verified implementation under [`rust/`](../rust/) and does not redefine or replace the existing Python implementation.

## Scope

The Rust MVP covers four crates in the Cargo workspace:

* [`rust/protocol`](../rust/protocol/) defines the event envelope, subject constants, and runtime payload structures.
* [`rust/bus`](../rust/bus/) provides an in-memory publish/subscribe bus for local runtime execution and tests.
* [`rust/runtime`](../rust/runtime/) provides runtime lifecycle state, task tracking, worker lookup, MVP LLM mediation, MVP tool mediation, handler registration, and bus-backed publish/handle behavior.
* [`rust/cli`](../rust/cli/) provides the local command surface, including the deterministic demo path.

The MVP keeps the Python runtime path compatible with the broader project. Rust is documented as an implemented workspace subset, not as a replacement for Python.

## Protocol Contract

[`EventEnvelope`](../rust/protocol/src/message.rs:5) is the Rust runtime event envelope. It includes canonical fields for `id`, `type`, `subject`, `source`, `timestamp`, `schema`, `payload`, `correlation_id`, `causation_id`, and `metadata`, plus optional current extension fields `scope` and `refs`.

[`EventEnvelopeFields`](../rust/protocol/src/message.rs:26) is the constructor input for [`EventEnvelope::new()`](../rust/protocol/src/message.rs:44). This keeps envelope construction explicit while preserving serde-compatible public fields.

Runtime payloads live in [`rust/protocol/src/payload.rs`](../rust/protocol/src/payload.rs). The MVP includes [`RuntimeTaskAssignPayload`](../rust/protocol/src/payload.rs:10), [`RuntimeTaskResultPayload`](../rust/protocol/src/payload.rs:24), [`RuntimeAgentReadyPayload`](../rust/protocol/src/payload.rs:34), [`RuntimeAgentExitPayload`](../rust/protocol/src/payload.rs:41), [`RuntimeToolRequestPayload`](../rust/protocol/src/payload.rs:47), [`RuntimeToolResultPayload`](../rust/protocol/src/payload.rs:56), [`RuntimeLLMRequestPayload`](../rust/protocol/src/payload.rs:66), [`RuntimeLLMResponsePayload`](../rust/protocol/src/payload.rs:78), and [`RuntimeAgentErrorPayload`](../rust/protocol/src/payload.rs:91). Payload-level `correlation_id` is carried by task, LLM, and tool request/result payloads so the runtime can preserve request correlation independently of generated event envelope ids and timestamps.

Subject constants live in [`rust/protocol/src/subject.rs`](../rust/protocol/src/subject.rs). The MVP includes agent spawn/ready/exit/error subjects, task assign/result subjects, LLM request/response subjects, and tool request/result subjects. Dynamic task assignment subjects are generated by [`runtime_task_assign_for_agent()`](../rust/protocol/src/subject.rs:8).

## Bus Contract

[`BasicBus`](../rust/bus/src/lib.rs:84) is the in-memory MVP bus. It stores subscribers by subject, tracks whether the bus is closed, and records published envelopes for observation.

The [`MessageBus`](../rust/bus/src/lib.rs:59) contract supports subscribe, publish, unsubscribe, close, closed-state inspection, and handler-count inspection.

Current publish semantics are:

* [`publish()`](../rust/bus/src/lib.rs:146) returns a closed-bus error if the bus has been closed.
* Publishing to a subject with no subscribers succeeds.
* Every accepted envelope is appended to [`published_events()`](../rust/bus/src/lib.rs:101) before handler execution completes.
* Matching handlers are invoked asynchronously and handler task failures are mapped to the bus protocol error path.

These semantics support deterministic local testing without requiring NATS for the MVP path.

## Runtime Contract

[`ThalamusRuntime`](../rust/runtime/src/lib.rs:382) owns a bus, lifecycle state, registered event handlers, spawned task handles, a worker registry, and task state storage.

The lifecycle state is represented by [`RuntimeState`](../rust/runtime/src/lib.rs:34). New runtimes start in the initialized state, [`start()`](../rust/runtime/src/lib.rs:726) transitions through starting to running, and [`stop()`](../rust/runtime/src/lib.rs:774) transitions running runtimes through stopping to stopped while closing the bus.

Task and worker support is implemented for the MVP runtime semantics:

* [`TaskStatus`](../rust/runtime/src/lib.rs:68) maps runtime status strings into task states used by the in-memory runtime store.
* [`TaskState`](../rust/runtime/src/lib.rs:108) stores a task id, optional assigned agent, and status, then updates assignment and result state through async mutators.
* [`WorkerState`](../rust/runtime/src/lib.rs:166) represents ready, exited, and error worker states.
* [`WorkerRegistry`](../rust/runtime/src/lib.rs:233) registers worker ids with capability lists, tracks worker state, records exit/error reasons, supports lookup by id, and supports capability lookup.
* [`spawn()`](../rust/runtime/src/lib.rs:430) returns a task handle and tracks active spawned futures until completion.

MVP mediation components are deterministic and local:

* [`MockLlmProvider`](../rust/runtime/src/lib.rs:334) returns a completed mock response using the request `prompt` or the last `messages` content, plus the requested model or the default mock model, and preserves the request payload `correlation_id`.
* [`EchoTool`](../rust/runtime/src/lib.rs:366) returns the request input as the tool output and preserves the request payload `correlation_id`.

Default runtime subjects are registered by [`ensure_default_handlers()`](../rust/runtime/src/lib.rs:473) for agent spawn/ready/exit/error, task assign/result, LLM request, and tool request. [`publish()`](../rust/runtime/src/lib.rs:797) first publishes the accepted input envelope through the bus, then applies default runtime behavior through [`handle_event()`](../rust/runtime/src/lib.rs:817). Agent ready events register ready workers, agent exit/error events update worker state, task assign events create or update assigned task state, and task result events update task status. LLM requests mark the related task as waiting for LLM before publishing a deterministic [`MockLlmProvider`](../rust/runtime/src/lib.rs:334) response through [`publish_default_runtime_result()`](../rust/runtime/src/lib.rs:634). Tool requests similarly mark the related task as waiting for a tool before publishing an [`EchoTool`](../rust/runtime/src/lib.rs:366) result through the same bus-mediated path. Accepted events remain observable through the bus even when there are no external subscribers.

## MVP Semantic Completion Contract

The semantic completion scope is limited to the Rust Runtime MVP crates already listed in this document. It completes the observable meaning of the current protocol, bus, runtime, and CLI path; it does not introduce production NATS, MCP gateway mediation, Qdrant/indexer behavior, SDK/FFI expansion, ZooCodeCustom integration, or Python runtime changes.

Implemented protocol semantics:

* [`EventEnvelope`](../rust/protocol/src/message.rs:5) keeps `scope` and `refs` as optional structured [`serde_json::Value`](../rust/protocol/src/message.rs:14) fields. Contract tests must prove the fields can carry object/array JSON values and default to `None` when omitted.
* Runtime task payloads and task state use a single explicit state machine: assignment creates or updates a pending/running task, task result completes it, and agent error/exit handling must not invent unrelated task states.
* LLM and tool result envelopes set `correlation_id` and `causation_id` to the request event id, while payload-level `correlation_id` remains the request payload correlation value.

Implemented runtime semantics:

* [`WorkerRegistry`](../rust/runtime/src/lib.rs:233) is stateful: ready/spawn-like registration records capabilities, exit/error marks an existing worker inactive or failed, and lookup by worker id returns the latest record.
* Default handlers cover agent lifecycle, task assign/result, LLM request, and tool request subjects. Publishing an accepted envelope succeeds even when no external handler is subscribed.
* [`ThalamusRuntime::publish()`](../rust/runtime/src/lib.rs:797) remains the sole event-flow entry point for these MVP semantics: it first publishes the accepted envelope to the bus and then applies default runtime behavior.

Implemented CLI semantics:

* [`RunDemo`](../rust/cli/src/lib.rs:37) demonstrates the runtime event flow through [`ThalamusRuntime::publish()`](../rust/runtime/src/lib.rs:797), not by bypassing runtime mediation. The expected observable markers stay `Runtime Event Flow`, `Mock response: summarize runtime MVP`, and the echo tool JSON outcome.

The current MVP semantics are implemented and verified by the Rust workspace checks listed below.

## CLI Contract

[`ThalamusCLI`](../rust/cli/src/lib.rs:11) defines the command-line surface. [`CLICommand`](../rust/cli/src/lib.rs:23) includes start, stop, status, list-agents, and [`RunDemo`](../rust/cli/src/lib.rs:37).

[`ThalamusCLI::run()`](../rust/cli/src/lib.rs:60) currently completes the local command paths without external services. [`RunDemo`](../rust/cli/src/lib.rs:90) is the MVP demo command path: it creates [`ThalamusRuntime`](../rust/runtime/src/lib.rs:199) with [`BasicBus`](../rust/bus/src/lib.rs:84), starts the runtime, publishes a [`RuntimeLLMRequestPayload`](../rust/protocol/src/payload.rs:75) with the prompt `summarize runtime MVP`, and publishes a [`RuntimeToolRequestPayload`](../rust/protocol/src/payload.rs:50) with `{ "text": "runtime MVP" }`. The observed CLI output is deterministic: `Runtime Event Flow`, `Mock response: summarize runtime MVP`, and the echo tool JSON outcome. The CLI manifest declares [`thalamus-protocol`](../rust/cli/Cargo.toml:8) and [`serde_json`](../rust/cli/Cargo.toml:11). The current CLI behavior is covered by the Rust workspace test artifact [`cargo-test-after-messages.log`](../artifacts/test-results/cargo-test-after-messages.log:1).

## Non-goals

The Rust MVP does not claim the following:

* Replacement of the existing Python implementation.
* Production NATS backend behavior for the Rust bus path.
* External MCP gateway mediation.
* Real LLM provider integration.
* Coverage percentage, security pass status, or performance benchmark results.
